# Spatial Agent 项目总体方向

本文档作为持续开发 goal 规划下一阶段任务时的总体参考。阶段任务必须服务于完整 Agent 闭环，不能因为最近出现的单个数据、模型或页面问题而改变项目主线。

## 项目定位

Spatial Agent 是一个可演示、可测试、可扩展的空间智能体系统。GIS 数据是业务载体，核心目标是展示 Agent 的任务理解、计划编排、工具执行、结果解释和可靠运行能力。

## 当前总体 Goal

建设一个通用、可组合、可解释的空间智能体，而不是围绕某个行政区和某个分析问题不断增加规则分支。系统应从自然语言中独立抽取空间实体、任务意图、数据需求、约束条件和输出证据，再由能力目录、工具 schema 与统一 Planner/Runtime 契约动态组合多工具 DAG。

新增区域或功能应主要通过实体解析、能力声明、工具契约和结果类型扩展，而不是增加“区域 × 功能 × 表达方式”的专用判断。规则规划器作为离线确定性兜底，真实模型作为开放式理解入口，两者必须产出兼容的 `TaskPlan` 并经过同一套安全门控、数据健康检查、执行、证据和恢复链路。

上下文工程也必须服务于整体 Agent 闭环：内部 Context 用于校验、恢复和证据，模型 Envelope 只携带当前规划阶段必需的最小投影；二者使用独立预算，不能通过把所有内部信息发送给模型来换取成功率。

后续阶段持续执行：

```text
全局能力盘点 -> 通用请求建模 -> 能力发现与组合编排 -> 受控执行
-> 动态答案/地图/轨迹/证据 -> 跨区域跨问题测试 -> 全局重规划
```

洪山区综合空间分析仅作为复杂回归样例，不再作为系统设计中心。

### 当前阶段 Goal（精简版）

建设 Agent Runtime 的实时交互与可观测体验：用户提交开放式问题后，能够持续看到真实的阶段进展、工具状态、可审计摘要和最终答案流，并在断线、重启或失败后恢复。

本阶段只保留五项主线：

1. 用版本化 `RunEvent` 统一表达生命周期，并让 CLI、HTTP、前端和恢复流程共享同一事件、结果与证据契约。
2. 提供 SSE、`Last-Event-ID`、断线/重启恢复和 polling fallback；真实模型只输出经过校验的计划、工具参数和答案增量。
3. 前端突出答案和结构化结果，按需展示地图、证据、轨迹、当前动作、心跳、耗时、错误与恢复进度；分析摘要默认收起，不展示隐藏思维链、Prompt 或敏感信息。
4. 支持取消、重试、失败恢复，并保持跨入口核心结果和证据一致。
5. 采用单 Agent 顺序开发：全局规划 → Spec → Plan → 实现 → 最小必要验证 → 交接记录 → 全局重规划 → 提交推送；最大并发度为 1，不启动并行子代理。

阶段验收以一条复杂开放式请求、断线/重启恢复、一次真实模型 + Docker/GIS 验收为主；默认测试保持离线、精简且按独立风险集中执行。

### Goal 新增执行约束：更完整的阶段包与低频验证

为降低上下文切换和重复反馈成本，后续阶段不得按单个文件、单个函数或单个测试用例拆成大量微阶段。每个阶段应尽量编排一个更完整的能力切片，至少覆盖：全局缺口确认、契约/接口设计、核心实现、跨入口集成、文档与交付准备，以及阶段收口所需的风险验收。只有存在明确依赖、独立阻塞或不同交付边界时，才拆分子任务。

阶段任务安排应比当前最小实现单元更充实：在同一能力链上尽量一次纳入多个相互依赖、可以连续交付的任务，直到形成可独立验收的阶段增量；不要因为任务数量变多而增加同等数量的测试轮次。

测试采用“集中实现、统一验证”的节奏：开发过程中只运行能快速暴露当前独立失败模式的必要检查；相关任务完成后统一运行一次精简阶段门禁。默认门禁只保留核心契约、关键跨入口一致性、编译/架构检查和 readiness；不为每个小改动重复运行相同测试，也不因为阶段任务变多而线性复制测试例。真实模型、真实 GIS、Docker、HTTP、浏览器和完整回归只在风险确实涉及或阶段收口需要时显式执行，并记录可复用的验收证据。

因此，阶段规划优先合并同一能力链上的多个任务（规划、实现、集成、文档和交付准备），让每个阶段产出可独立验收的完整增量；测试数量以独立风险为上限，而不是以任务数量为基数。一个阶段内共享同一套精简门禁结果，只有代码边界或失败模式发生实质变化时才增加测试。

### Goal 新增执行约束：唯一交接入口与实现优先

`docs/agent-work-state.md` 是 Goal 的唯一默认交接文档，也是上下文压缩或新对话后的
第一读取入口。它必须在文件顶部保持一份短快照，至少包含：当前 Goal 摘要、当前阶段、
正在进行的完整任务包、阶段 Spec/Plan 指针、明确需要修改的文件、已做出的关键决策、
最近一次有效验证、阻塞、未提交变更和下一步动作。不要为同一目的继续创建第二份当前快照。

`tasks/task-progress.md` 只承担短任务账本：顶部固定保留“当前进行中”和“最近完成”两个
有界区块；每条记录只写目标、状态、实际改动文件、验证、阻塞和下一步。旧记录移入历史
区块，不得挤占当前交接信息。`tasks/task-state.md`、`docs/agent-context-resume.md`、
`docs/milestones.md`、问题日志和归档仅按需读取，不属于默认恢复输入。

上下文压缩后的最小读取顺序固定为：

1. 优先读取 `docs/agent-context-resume.md` 和 `docs/task-resume.md` 的入口规则（不读取其中的历史正文）；
2. 读取 `docs/agent-work-state.md` 顶部快照；
3. 读取 `tasks/task-progress.md` 的当前进行中和最近完成有界区块；
4. 仅按快照中当前任务列出的 Spec/Plan 和源码/测试文件逐项读取；
5. 只有发现直接依赖或需要追溯具体问题时，才使用主题检索读取其它文件。

仅判断状态时只读第 1 步。恢复不得批量读取全量源码、全量测试、历史文档、模型原文、
完整日志、真实原始数据或敏感配置。每个任务开始、完成或暂停时先更新任务账本和快照，
使下一次恢复不依赖本轮对话记忆。

Goal 的主要上下文预算应投入契约设计、核心实现、集成和代码审查。测试实行风险驱动的
低频策略：开发中只做必要的语法、类型、diff 和当前独立失败模式检查；相关代码完成后
集中运行一次精简阶段门禁。测试例不按任务数线性增加，不为同一失败模式重复跑测试；只
在公共边界、失败模式或交付风险发生实质变化时增加验证。真实模型、Docker、GIS、HTTP
和浏览器验收按阶段需要显式执行，并复用已有证据，避免为了“多测几次”消耗实现上下文。

### Goal 新增执行约束：单 Agent 顺序开发

当前开发最大并发度为 1，由单一 Agent 顺序负责规划、实现、集成、验证、文档和推送。
不启动并行子代理，不使用 `codex exec`、tmux 或外部协调器；这样可以减少上下文、Provider
限流和共享工作树冲突。长期记忆以 `docs/agent-work-state.md`、`tasks/task-progress.md`
和当前阶段 Spec/Plan 为权威，同一主对话的上下文只作为恢复缓存。

## Goal 执行与上下文恢复约束

Goal 的每个阶段都必须留下一个短的、可恢复的工作状态，而不是要求下一次对话重新读取全部历史。`docs/agent-work-state.md` 是新对话或上下文压缩后的唯一默认入口，负责提供当前 Goal、阶段规划指针和恢复规则；`tasks/task-progress.md` 是进行中/最近完成子任务的短账本，记录目标、改动文件、验证、阻塞和下一步；`tasks/task-state.md` 只保留兼容性的详细当前状态；`tasks/todo.md` 只作为简短阶段清单。

Goal 的正式最小读取约束是：恢复或继续任务时，只读取当前任务明确必需的文件；仅做状态判断时只读取工作快照和任务账本尾部。发现新的直接依赖后，才登记并读取该文件，不得因熟悉项目而批量加载历史文档、全量源码、全量测试、模型原文或无关数据。

恢复时只读取工作快照、任务进度账本的最近记录、当前阶段对应的 Spec/Plan、最近进行中任务和该任务明确列出的源码/测试文件。该最小读取规则是 Goal 的正式执行约束，不是可选建议。历史恢复卡、问题日志、milestones、归档、详细任务状态、全量测试、模型原文和无关源码必须按需读取，不能作为默认输入。每个子任务开始、完成或暂停时，先更新任务进度账本，再更新工作快照和详细状态；阶段完成后同步中文历史文档、提交并推送版本，然后基于项目全局重规划下一阶段。每个阶段应编排更完整的任务包，覆盖从契约、实现、集成到交付的主要依赖链，减少频繁拆成过小阶段造成的上下文切换。测试只保留能覆盖独立失败模式和跨入口契约的必要验收，避免重复调用；同一阶段集中完成相关实现后统一验证，不为每个小改动重复跑测试。

## 核心闭环

```text
自然语言问题
  -> 意图识别与必要澄清
  -> 结构化计划与约束校验
  -> 多工具编排与受控执行
  -> 答案、地图、轨迹和数据证据
  -> 会话恢复、异步运行、重试与评测
```

## 必须持续建设的能力

1. **任务与规划**：开放式问题理解、澄清、多步骤计划、依赖关系、计划修复。
2. **工具与架构**：统一 schema、Tool Registry、Planner/Runtime/Backend 解耦和安全边界。
3. **状态与可靠性**：会话历史、异步任务、取消、超时、幂等、重启恢复和可观测性。
4. **结果与证据**：统一 result envelope，关联答案、轨迹、工具结果、GeoJSON、地图图层、数据版本和 provenance。
5. **模型工程**：真实模型可替换、结构化输出校验、失败分类、重试、token/延迟指标和离线回放。
6. **数据与 GIS**：数据健康、覆盖范围、CRS/栅格对齐、manifest 和降级说明；数据问题只能作为系统能力的证据层。
7. **产品体验**：对话驱动、按结果类型动态展示答案、表格、地图、下载项和轨迹，避免固定堆叠无关面板。
8. **测试与部署**：契约测试、端到端评测、浏览器 smoke、真实 GIS 验证、Docker、readiness 和生产接口验收。

## 阶段规划原则

产品 Runtime 的公共契约、阶段实现和集成均按串行方式执行，最大并发度为 1。每次规划下一阶段，先从产品、架构、数据、模型、部署、体验、测试七个维度盘点现状、缺口、依赖、风险和验收证据。

具体数据集、单个工具、一次模型报错或一个页面缺陷，必须明确说明它服务于哪个系统级目标；不能把局部修复本身当作下一阶段目标。阶段任务数量应以完整能力切片为准，而不是以单个文件或单个测试用例为准。

阶段循环固定为：

```text
全局盘点 -> 阶段规划 -> 顺序实现 -> 统一集成 -> 分层测试 -> 全局复盘 -> 下一阶段
```

## 面试展示标准

最终演示应能完整回答一个开放式空间问题，并让面试官看到：Agent 如何决策、为什么调用这些工具、结果是否可信、失败如何恢复、系统如何测试和部署。新增功能只有在增强这条证据链时才优先进入规划。
