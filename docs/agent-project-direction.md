# Spatial Agent 项目总体方向

本文档作为持续开发 goal 规划下一阶段任务时的总体参考。阶段任务必须服务于完整 Agent 闭环，不能因为最近出现的单个数据、模型或页面问题而改变项目主线。

## 项目定位

Spatial Agent 是一个可演示、可测试、可扩展的空间智能体系统。GIS 数据是业务载体，核心目标是展示 Agent 的任务理解、计划编排、工具执行、结果解释和可靠运行能力。

## 当前总体 Goal

建设一个通用、可组合、可解释的空间智能体，而不是围绕某个行政区和某个分析问题不断增加规则分支。系统应从自然语言中独立抽取空间实体、任务意图、数据需求、约束条件和输出证据，再由能力目录、工具 schema 与统一 Planner/Runtime 契约动态组合多工具 DAG。

新增区域或功能应主要通过实体解析、能力声明、工具契约和结果类型扩展，而不是增加“区域 × 功能 × 表达方式”的专用判断。规则规划器作为离线确定性兜底，真实模型作为开放式理解入口，两者必须产出兼容的 `TaskPlan` 并经过同一套安全门控、数据健康检查、执行、证据和恢复链路。

后续阶段持续执行：

```text
全局能力盘点 -> 通用请求建模 -> 能力发现与组合编排 -> 受控执行
-> 动态答案/地图/轨迹/证据 -> 跨区域跨问题测试 -> 全局重规划
```

洪山区综合空间分析仅作为复杂回归样例，不再作为系统设计中心。

### Goal 新增执行约束：完整阶段包与低频验证

为降低上下文切换和重复反馈成本，后续阶段不得按单个文件、单个函数或单个测试用例拆成大量微阶段。每个阶段应尽量编排一个更完整的能力切片，至少覆盖：全局缺口确认、契约/接口设计、核心实现、跨入口集成、文档与交付准备，以及阶段收口所需的风险验收。只有存在明确依赖、独立阻塞或不同交付边界时，才拆分子任务。

测试采用“集中实现、统一验证”的节奏：开发过程中只运行能快速暴露当前独立失败模式的必要检查；相关任务完成后统一运行一次精简阶段门禁。默认门禁只保留核心契约、关键跨入口一致性、编译/架构检查和 readiness；不为每个小改动重复运行相同测试，也不因为阶段任务变多而线性复制测试例。真实模型、真实 GIS、Docker、HTTP、浏览器和完整回归只在风险确实涉及或阶段收口需要时显式执行，并记录可复用的验收证据。

因此，阶段规划优先合并同一能力链上的多个任务（规划、实现、集成、文档和交付准备），让每个阶段产出可独立验收的完整增量；测试数量以独立风险为上限，而不是以任务数量为基数。一个阶段内共享同一套精简门禁结果，只有代码边界或失败模式发生实质变化时才增加测试。

## Goal 执行与上下文恢复约束

Goal 的每个阶段都必须留下一个短的、可恢复的工作状态，而不是要求下一次对话重新读取全部历史。`docs/agent-work-state.md` 是新对话或上下文压缩后的唯一默认入口，负责提供当前 Goal、阶段规划指针和恢复规则；`tasks/task-progress.md` 是进行中/最近完成子任务的短账本，记录目标、改动文件、验证、阻塞和下一步；`tasks/task-state.md` 只保留兼容性的详细当前状态；`tasks/todo.md` 只作为简短阶段清单。

恢复时只读取工作快照、任务进度账本的最近记录、当前阶段对应的 Spec/Plan、最近进行中任务和该任务明确列出的源码/测试文件。历史恢复卡、问题日志、milestones、归档、详细任务状态、全量测试、模型原文和无关源码必须按需读取，不能作为默认输入。每个子任务开始、完成或暂停时，先更新任务进度账本，再更新工作快照和详细状态；阶段完成后同步中文历史文档、提交并推送版本，然后基于项目全局重规划下一阶段。每个阶段应编排更完整的任务包，覆盖从契约、实现、集成到交付的主要依赖链，减少频繁拆成过小阶段造成的上下文切换。测试只保留能覆盖独立失败模式和跨入口契约的必要验收，避免重复调用；同一阶段集中完成相关实现后统一验证，不为每个小改动重复跑测试。

## 核心闭环

```text
自然语言问题
  -> 意图识别与必要澄清
  -> 结构化计划与约束校验
  -> 多工具编排与受控执行
  -> 答案、地图、轨迹和数据证据
  -> 会话恢复、异步运行、重试与评测
```

## 必须持续建设的能力

1. **任务与规划**：开放式问题理解、澄清、多步骤计划、依赖关系、计划修复。
2. **工具与架构**：统一 schema、Tool Registry、Planner/Runtime/Backend 解耦和安全边界。
3. **状态与可靠性**：会话历史、异步任务、取消、超时、幂等、重启恢复和可观测性。
4. **结果与证据**：统一 result envelope，关联答案、轨迹、工具结果、GeoJSON、地图图层、数据版本和 provenance。
5. **模型工程**：真实模型可替换、结构化输出校验、失败分类、重试、token/延迟指标和离线回放。
6. **数据与 GIS**：数据健康、覆盖范围、CRS/栅格对齐、manifest 和降级说明；数据问题只能作为系统能力的证据层。
7. **产品体验**：对话驱动、按结果类型动态展示答案、表格、地图、下载项和轨迹，避免固定堆叠无关面板。
8. **测试与部署**：契约测试、端到端评测、浏览器 smoke、真实 GIS 验证、Docker、readiness 和生产接口验收。

## 阶段规划原则

当前 goal 按串行方式实施（最大并发度为 1）。每次规划下一阶段，先从产品、架构、数据、模型、部署、体验、测试七个维度盘点现状、缺口、依赖、风险和验收证据；即使未来恢复并行，也必须由主线统一集成和验收。

具体数据集、单个工具、一次模型报错或一个页面缺陷，必须明确说明它服务于哪个系统级目标；不能把局部修复本身当作下一阶段目标。阶段任务数量应以完整能力切片为准，而不是以单个文件或单个测试用例为准。

阶段循环固定为：

```text
全局盘点 -> 阶段规划 -> 顺序实现 -> 统一集成 -> 分层测试 -> 全局复盘 -> 下一阶段
```

## 面试展示标准

最终演示应能完整回答一个开放式空间问题，并让面试官看到：Agent 如何决策、为什么调用这些工具、结果是否可信、失败如何恢复、系统如何测试和部署。新增功能只有在增强这条证据链时才优先进入规划。
